Skowork

The company AI agent for Windows laptops: governed, on-premise, and private by default.

Use ← → or click the edges to move through the deck
The problem

Knowledge work is spread across many tools, and AI must stay governed

Mail and calendar

Microsoft 365 mailboxes and meetings hold decisions and follow-ups.

Documents and files

Reports, specifications and notes sit in local folders and on the laptop.

Chats and line-of-business apps

Colleagues talk in chats; many desktop applications have no API.

Routine work

Weekly reports, supplier triage and change reviews repeat every week.

AI must run on company-controlled models

Credentials and model keys stay on company servers, not on laptops.

Actions must stay within policy

Anything that sends, writes or deletes needs a rule, and often a person's approval.

INTERNAL2 / 17
What Skowork is

One agent per employee, managed centrally

1

On the laptop

A Windows desktop client runs as the signed-in user, with a tray icon and encrypted local storage. All user data stays local.

2

In the company

A control plane on company servers handles sign-in, policy, Groups, the LLM gateway, the approved MCP catalog, the fleet and the admin console.

3

Models

The company LLM API serves all model calls through the gateway. Laptops never hold model keys and never call model servers directly.

Work happens in Threads. The agent asks for approval when policy requires it, and it never acts beyond what the user's Groups allow.

Architecture overview

Three places, one controlled path for every request

INTERNAL4 / 17
How a Run works

A Run moves through the model, tools, policy and, when needed, a person

1

Request

A user message, a Trigger or a Remote task starts a Run in a Thread.

2

Model

The main model role, through the gateway, plans the next step.

3

Tool call

The tool declares its Risk class: read, write-local, external or destructive.

4

Policy

Allow, approve or deny. The decision comes from the user's effective policy.

5

Action item

On approve, the Run pauses and waits for a person in the Inbox. It resumes once.

6

Result

The result returns to the model as untrusted data, and is kept in the Thread.

Rule: an approval is resolved only by an explicit action in the client. Text inside an email, web page or file cannot approve anything.

Governance: policy

Every tool call gets exactly one decision

1 · Org guardrail

Applies to everyone. Can only make things stricter; Groups cannot override it.

2 · Groups

Standard, power-user, developer, region-cz. Deny wins across Groups; lists are merged.

3 · User

Folder grants and choices inside the bounds set above.

A signed, expiring policy bundle is delivered per user. Policy changes reach clients by push.

INTERNAL6 / 17
Governance: containment

Anything the agent runs is contained, and untrusted content cannot grant rights

Process sandbox

Shell and tools run contained

  • Child processes run in Job Objects with memory, CPU and process limits
  • Reduced token, no admin rights
  • Shell mode: off, sandboxed or allow (default off)
Network egress

Every outbound request is checked

  • Allow and deny host rules apply to web fetch, MCP, browser and sandboxed processes
  • Child processes use a local egress proxy
  • No-network mode refuses every destination
Untrusted content

Data, never commands

  • Email, web pages, files, transcripts, MCP results and Remote task prompts are tagged with their source
  • They cannot change a decision or resolve an approval
  • No valid policy bundle: only reads of the client's own data run

INTERNAL8 / 17
Automation

Work that starts without typing

Skills

Reusable SKILL.md packages

A skill captures how a task is done. Tiers: built-in, org, group, shared, private. Org-wide skills need an automated scan, a reviewer's approval and signing. Installed versions are pinned and can be revoked centrally.

Triggers and Occurrences

Schedule, file, mail, calendar, meeting

A Trigger starts a Run. Each firing is an Occurrence, retried up to three times. These Runs are Unattended: the stricter unattended rules apply, and any approval waits for a person.

Remote tasks

Requested by people or systems

Colleagues or systems such as Jira or CI request work through a control-plane API. The target user consents the first time. A Remote task is not a Trigger.

Inbox results

Results arrive as Threads

Every automated Run lands in the Inbox like any other Thread. Action items appear in the Action view. The tray shows the count.

Connected tools and small apps

Only approved MCP servers, and apps that run without network

MCP servers

From an admin catalog

  • The client connects only to servers assigned to the user's Groups
  • Local packages are pinned by SHA-256 and checked on every start
  • Tools appear as mcp:<server>/<tool>; results are untrusted; the default risk is external
Local apps

Small apps the agent builds for one user

  • Node.js, HTML, CSS and SQLite, built-in modules only
  • Runs in a contained process with no network access
  • Opens for the user only, on a loopback address in their browser
  • Reads live data from approved read-only MCP tools

Telemetry and privacy

Metadata by default; content only after company-level approval

off
metadata (default)
content

Metadata

Operational signals: health, usage and failures. The default level.

Content

Adds content. The user sees a persistent indicator. Production use needs the company approval process.

Viewer and buffer

Users can see what was sent. Records wait in an encrypted buffer, capped at 20 MB, and are forwarded over OTLP to the company SIEM.

INTERNAL14 / 17
Deployment and operations

Two release artifacts, a light client, and clear offline behaviour

Installed like any app

  • Windows 11 x64, signed in user
  • No admin rights, no service, no driver
  • Delivered by the company software distribution system

Lean footprint

  • Core package 25 MB or less
  • Idle working set 60 MB or less, with the window closed
  • Tray ready within 2 seconds

Offline for a day or more

  • Threads, local search and notes keep working: all data is local
  • New requests wait in their Thread and start on reconnect
  • The session survives network failures; the policy is valid for 7 days
  • Chats, sharing and policy updates wait for the connection
