## Goals / Non-Goals

**Goals:** consistent product identity; discoverable policies; speech that can be set up by an ordinary user; bounded long-running context; and a knowledge workspace where a person can explain both why something is believed and who can see it.

**Non-goals:** a new storage service or graph database, a new authentication scheme, a general updater, an automatic truth arbiter, or background publication inferred from category membership. Native client UI and the existing encrypted stores remain the architecture.

## Decisions

### D1. Separate product identity from compatibility identifiers

Use SkoWork for localized UI strings, executable resource metadata, admin browser title and visible copy. Set the primary executable output to `SkoWork.exe` and desktop zip prefix to `SkoWork-`. Update tests, signing, footprint checks, launch/dev scripts and package manifests that resolve the executable. Keep a small `Workbench.exe` compatibility launcher using the same single-instance path; forward the supported argument vector without concatenating a shell command. Identify both executable names as the client's own windows for computer-use refusal.

Keep existing data roots, mutex/pipe identifiers, DPAPI bindings, OIDC client identifiers, `WORKBENCH_*` settings, established endpoint paths and `workbench-team://` citations. New branding does not justify changing any of those contracts. Product guidance in `openspec/` and `config.yaml` is updated; historical evidence stays historical. Do not mass-replace namespace symbols, comments or archived designs.

The desktop and speech worker each embed their own Windows manifest. For MinGW GCC versions that inject `default-manifest.o` through the known `endfile` specification, generate a build-local override that removes only that injection for those targets; preserve all other toolchain end files. Fail configuration if an unrecognized default-manifest injection is present rather than guessing. Verify the linked resources and Unicode worker startup on the actual release toolchain; never modify the compiler installation.

Alternatives: rename only the window (leaves a visibly mixed product); globally replace Workbench (breaks credentials, launch scripts and citations); duplicate the full executable under both names (unnecessarily consumes the core footprint).

### D2. A complete catalog over the existing policy semantics

Extend the key registry's metadata with concise labels/descriptions and a versioned built-in Tool catalog. Each Tool record has id, owner, base risk, dynamic-risk explanation, feature/role prerequisites and valid pattern examples. Prefer a declarative manifest consumed by catalog generation and client registration checks; it is not a second policy evaluator. MCP entries come from the existing authorized catalog and discovery results, with the standard `mcp:<server>/<tool>` spelling.

The editor searches labels, paths, descriptions, Tool ids and existing patterns. Keep settings and decisions visibly distinct. Tool rows show inherited state until the admin opens an edit dialog, selects an attended/unattended context and deliberately chooses a decision. A searchable picker offers known Tools and wildcard patterns; custom valid patterns survive. Do not preselect allow when creating a rule. Link prerequisites such as computer mode and vision support.

Extend the existing policy simulation contract with a structured decision trace. Reuse `client/policy-enforcement` matching and precedence semantics through shared fixtures consumed by C++ and TypeScript tests; do not assume exact-match specificity or Group precedence independently. Dynamic action risk, target availability and user/device state remain conditional. Draft preview and selected-user effective policy are clearly labeled.

The initial tool simulation accepts a concrete Tool id, an explicitly displayed assumed risk and an attended/unattended choice. It reports a policy-only example with the rule, source and decision steps, and states that the actual target, resource checks, device and Skill can change the result. Shared fixtures exercise portable matching and floors in both implementations; the Windows enforcer separately checks the computer-mode switch. The administrator may include saved drafts; unsaved editor changes are not part of the simulation. This is partial coverage, not a guarantee of the decision on a particular device.

Coverage is bidirectional: owning specs/declared key inventory, server keys, generated `client/tests/fixtures/policy/schema.json`, actual client consumers/support declarations, all built-in Tool registration paths, catalog and rendered controls. The checker distinguishes references to a key from its owning declaration and dynamic map members from separate keys. Server-only policy consumers require an explicit owner; arbitrary blanket exclusions are not allowed. Existing tool registration tests exercise all feature combinations so a disabled capability is not omitted from the catalog.

Alternatives: a hardcoded dropdown of computer Tools (drifts immediately); treat every Tool as a new schema field (breaks the policy layout); show JSON alone (does not solve discoverability).

### D3. A complete optional speech package and a small setup flow

Reuse the pinned sherpa-onnx/ONNX CPU engine and existing Parakeet, Whisper fallback, VAD and diarization assets. This plan does not assert new upstream versions or unmeasured language quality. Factor the pinned identities, hashes, licenses, installed sizes and compatibility information out of `fetch-stt-models.ps1` into one machine-readable manifest used by build, download, verification and tests.

Build an immutable, versioned speech zip alongside each release/dev desktop. Compatible desktop versions may reference the same immutable package. The shipped core contains a trusted manifest digest and permitted distribution origins, including the organization's configured mirror; verify package and file hashes before loading DLLs. Mutable catalogs require authentication rooted in the shipped trust data, not a digest fetched from the same untrusted payload. Organization mirroring can change transport location without changing the accepted package bytes. Include licenses and omit developer audio fixtures from the shipped models.

Use the existing WinHTTP transport with proxy/PAC and certificate handling. Prefer the configured organizational package origin, provide a public product distribution origin when the release is configured for it, and always provide Import package. The URL is never typed by an end user or supplied by an agent. Control-plane bearer tokens go only to the configured control-plane origin, not to redirected artifact storage. A redirect must remain on an approved manifest origin. Acquisition is data delivery, not arbitrary executable updating.

Install into a versioned, user-private speech package directory under the data root, or use an administrator-deployed verified package beside the executable. Stage under that same allowed root, reject archive traversal, absolute/UNC paths, links, duplicate names, excess files and size inflation, verify required assets, then initialize the engine in the bounded worker and atomically switch the active-package record. Keep the prior working version until no worker holds it; clean failed staging on cancellation/startup. Offline import performs exactly the same checks. No elevation or background download on first launch.

Settings > Speech recognition uses states Not installed, Downloading, Verifying, Ready and Needs repair, with plain error details. Record progress without blocking the native UI. Test microphone is a separate explicit action. Install/verify events invalidate the current 30-second availability cache immediately. Device errors remain distinguishable from model errors in `DictationService` and `views_dictation.cpp`.

Alternatives: put 1+ GB into every core zip (violates lightweight distribution intent); require a PowerShell script (the reported defect); use hosted transcription (violates local-audio constraints); download arbitrary upstream tarballs at runtime (unbounded dependency and packaging variation).

### D4. Proactive context budget with a loss-accounted checkpoint

All limits in the spec are input tokens, not cumulative tokens billed across a conversation. Let W be the resolved model window, O the output limit actually allowed in the request, and H = max(4,096, ceil(0.02W)). Compute:

`B = min(W >= 1,000,000 ? 500,000 : 200,000, floor(0.8W), W - O - H)`

Trigger at `floor(0.9B)` and target `floor(0.6B)`, retaining mandatory messages even when the target is unattainable. Never send if the full re-estimated request is at or above B. Exactly 1,000,000 and 1,048,576 use the 500k tier; 262,000 and 262,144 use the 200k tier. An unknown model uses the existing conservative 32,768 fallback. If a role does not report a positive output limit, explicitly request and reserve 4,096 output tokens. Model remapping refreshes limits before a request. Small windows for which output plus reserves leave no room produce a useful error rather than wrapping unsigned arithmetic.

Account for the complete request, including tool schemas, images and framing. Prefer model-tokenizer counts where locally available without loading an ML model; otherwise use a conservative bounded estimate for UTF-8 text plus image/framing allowances, calibrated upward from provider prompt usage. Provider counts are evidence of prior requests, not a guaranteed count of the next one. Do not rely on `bytes / 4` for all languages. Expose estimates honestly. Keep the existing one context-length-error recovery, bounded by progress; repeated compaction with no reduction stops.

Replace Thread-only compaction input with a versioned context snapshot that joins the persisted checkpoint, current Run messages and in-flight state. Completed tool batches can be summarized within a long Run; unresolved call/result groups remain intact. Child Runs use their own snapshots. Keep the latest user instruction exactly, system instructions separately, and explicit durable constraints/decisions with provenance. Authorization, approvals, pending Questions and completed-effect records remain authoritative structured state outside generated summaries.

Summarize contiguous ranges that fit the small role's own input/output budget. Each range carries source message ids and revision; oversized messages are segmented at safe boundaries rather than cut at 2,000 characters. Include the previous summary explicitly. Merge bounded intermediate summaries and retain a coverage ledger proving every removed message was represented. Cache completed passes for retry, but publish a checkpoint only after complete coverage and revision compare-and-set. If new input arrives, reuse unchanged range summaries and rebase; never lose the new message. Summary content stays lower-trust conversational data with structured attribution, not text appended as authoritative system instructions.

The interim single-pass input uses one JSON object per message, with its stored Run id, sequence, role, tool-call ids and original text encoded as data. The previous summary is a separate object. Escaped source text cannot introduce another transcript record; this formatting does not itself prove model obedience or provide the required persisted coverage ledger.

Run BeforeCompaction hooks once per checkpoint attempt with an idempotency key. Persist one atomic checkpoint with boundary, carry-forward messages, coverage and usage. Preserve original history; forget invalidates affected summaries and their coverage records. On cancellation, timeout or failure keep the previous context. Compaction uses normal gateway budgets and cancellation. At most two full budget-reduction attempts per request; intermediate batch calls are bounded by coverage size and ordinary Run limits, and the UI shows progress.

Alternatives: lower 0.85 alone (misses active Runs and can discard content); truncate oldest messages (loses constraints); summarize 500k tokens in one small-model call (cannot fit); repeatedly prepend summaries to system instructions (promotes untrusted claims).

### D5. Four task-focused Knowledge sections

Use the existing native list/reader layout, with four section tabs, one persistent search field and filters for Source, category, status and audience. Default to Knowledge when content exists, and an empty state offering Add documents, Add folder and New note on a fresh profile. Sources remains one click away. UI strings explain effects instead of exposing schema vocabulary.

| Section | List and primary actions | Reader |
| --- | --- | --- |
| Sources | Source kinds, imports and connected items; Add, Pause, Recheck, Forget | Content / Extracted knowledge / Changes / Sharing; progress and errors |
| Knowledge | Categories, Uncategorized, facts and notes; organize and search | Statement, status, why it is here, evidence excerpts and original links |
| Review | Possible inconsistencies, changed evidence and suggested categories; filter by reason | Side-by-side claims, dates, evidence and explicit resolution choices |
| Sharing | Publications and explicit document/folder live shares; audience filters | Published content / Pending changes / Audience; preview and withdrawal actions |

Keep forms in dialogs, use pickers for known Groups, and preserve keyboard focus and scroll position. Source is the glossary's origin kind; the UI distinguishes an imported item/folder from that kind rather than redefining it. A Category is a user-editable organizational label, not a Group, Source or permission. Review entries are not Thread Action items. A Publication is the confirmed version of selected knowledge and excerpts visible to chosen Groups. Add these terms and ownership references to config context during implementation.

Example: the user imports a revised project plan. The preview says `12 new facts · 4 supported by another source · 2 possible disagreements · 1 published entry affected`. Clicking the disagreement opens `Deadline: 30 June` beside `Deadline: 15 July`, each with its actual passage and revision. Choosing `Use the approved plan` records a reason and evidence revisions; it does not edit either original document. A later supporting-source change reopens the decision.

Alternatives: make a graph visualization the main workspace (requires users to understand internal modeling); keep facts under a collapsed details panel (hides the requested controls); one large page with every form (conflicts with the user's established records-first interaction preference).

### D6. Versioned evidence before richer automation

Extend `kg.db` with migrations for item revisions, evidence spans, canonical facts, independent support sets, required derivation dependencies, user annotations, categories and assignment provenance, conflict candidates/resolutions, change batches, publication manifests and a durable outbox. Keep this in `KgStore` and `KnowledgeService`; split internal services only where needed for testable transactions, not into new processes.

Use stable item ids and content hashes, not only file size/mtime, for revision confirmation. A fact identity contains normalized subject, predicate, value, units, scope and validity interval; do not merge different people by ambiguous names or facts merely because an embedding is similar. Equivalent claims retain separate evidence supports. A derived conclusion requiring A and B uses one conjunctive support set; an independent proof from C is a separate support set. Deleting A invalidates the first proof without destroying the C proof. Cyclic derivations are refused, and reverse-dependency indexes support bounded cascades.

For the transition from legacy file fingerprints, a successful reindex uses a SHA-256 fingerprint of the bytes. If the previous fingerprint exactly matches the observed size and modification time, copy its deleted-fact tombstones to the new fingerprint in the same transaction as replacing the indexed item. This is conservative: legacy metadata cannot prove the previous bytes were identical. A file check that cannot read a complete, stable snapshot retains the prior item and reports the failure. Periodic checks must examine bytes even when size and time match; these checks run through the existing background indexing queue.

The current migration helper accepts an unrecognized higher database version, and existing released binaries therefore cannot be assumed to check it. A version check in the new client protects against later schema versions but does not protect the new schema against those already-released writers. Before activating the new schema, enforce its writer compatibility at the database boundary or provide an equally effective migration barrier; test it using an actual earlier writer against a copied encrypted profile. Rollback to an earlier binary requires the explicit, forget-aware restoration path below, not merely starting the old executable.

Register the knowledge writer capability on each new-client database connection before running migrations; keep it absent from other connections. A migration installs BEFORE INSERT/UPDATE/DELETE guards on every pre-existing mutable knowledge table in the same transaction as the new schema. The older writer reads and searches as before, but any attempted legacy table mutation fails at the SQLite boundary. Incompatible connections cannot authorize themselves by writing a metadata row. This is a compatibility barrier against older application code, not a security boundary against a malicious database administrator. Ensure a failed migration never leaves a partially guarded schema and account for encrypted migration backups before activating it: a confirmed forget must not leave a recoverable copy containing the forgotten data.

Fact lifecycle and user review are separate fields: current/disputed/superseded/unsupported/rejected describes use; automatic/confirmed/corrected describes review. Model confidence describes extraction quality only. User edits are explicit annotations and tombstones tied to source versions. They retain their dependencies for forget; they are not quietly transformed into free-standing facts that survive removal of their private Source. A genuinely independent user note must be deliberately created as a new Source.

Preserve historic evidence needed to explain a change within `policy.storage.max_size_gb`; do not retain whole raw files. History is not exempt from forget. Excerpts in facts, conflicts, previews, job caches and publications all have dependency links. UI retrieval never shows a snippet of a forgotten revision. Tombstones keep minimal identity/version fingerprints without its text, and exclusions prevent automatic re-ingestion. A pause keeps existing data and says it is stale; removing a watcher is not the same operation as forgetting stored data.

Before acknowledging an explicit knowledge forget or exclusion, remove the knowledge database's migration backup, if any; if removing it fails, return an error instead of reporting successful erasure. Item removal also deletes user-corrected facts whose provenance names that item, in the same database transaction as deleting the item. A source-wide removal deletes the corresponding item-provenanced corrections. This covers the existing `kg.db.bak` copy; staged revisions, other stores and remote withdrawal state still require the broader cascade specified below.

The Thread forget handler must propagate failures through the shared forget registry. It records a Thread item exclusion in the same transaction that deletes the indexed item, its item- or Thread-provenanced corrections and its old fact tombstones. The final indexing write checks that exclusion under the same database mutex; an already-running worker cannot reinsert the forgotten Thread.

The existing migration runner previously ignored both checkpoint errors and SQLite's successful-but-busy checkpoint result before copying the main encrypted file. It must reject a blocked checkpoint before touching the backup. This check alone does not prevent a separate writer from committing after the checkpoint and before the copy. For knowledge migrations, hold a SQLite immediate writer transaction, take an encrypted SQLite backup through a separate reader connection into a staging file, atomically replace the backup only after the snapshot is complete, and run every pending migration in that same writer transaction. Rollback leaves the database at its original version without overwriting another process's database file. The connection-local writer guard and new schema commit together, so a waiting older writer cannot mutate the migrated legacy tables after commit. Clean abandoned encrypted backup staging files during forget as well as the committed recovery copy.

Deleting a note removes the note, indexed item, item-provenanced corrections and text-bearing tombstones in one transaction, including when indexing never completed. The recovery copy is removed while that transaction holds the database writer reservation, and its removal failure prevents success. Indexing rechecks that the original note still exists while holding the same database mutex.

As an interim measure for existing item shares, a forget transaction converts active share rows into pending withdrawals before deleting their local items. It retains the remote identity in the encrypted store while clearing titles, groups, hashes, size, errors, rules and local item identifiers. Existing item-share synchronization retries these rows and cannot treat an absent team connection as successful withdrawal. Source-wide file forget also removes automatic folder share rules. This does not replace the identity-bound publication outbox needed for Delete all, account changes and versioned publication entries.

Applying exclusions serializes with existing item-share synchronization. It reports item-removal failures to an explicit exclusion request; periodic reconciliation logs failures and retries instead of silently claiming the content was removed.

Existing item sharing keeps the client-supplied content hash for backwards-compatible responses, but a separately stored server SHA-256 digest determines whether the uploaded bytes changed. Rows created before this digest was added are reprocessed on the next upload rather than trusting their old hash.

A mention records which name of an entity a passage used, so it is keyed by passage, entity and normalized name, not by passage and entity alone. Under the narrower key a merge of two entities named in the same passage silently dropped the merged-in name's mention; that name then had no accessible evidence, disappeared from the profile and could not be split back. Production migration 5 rebuilds `mentions` with the wider key and copies every row; the gated evidence schema moves to version 6 (`kKgEvidenceSchemaVersion`). The wider key only admits more rows, so writers that predate it keep working against the migrated table and no writer barrier is needed for this step. A split keeps the existing rule that relations from the passages mentioning the split name move with it; a passage that mentions both names cannot say which entity its relation was about.

Alternatives: attach only one chunk to each relation (cannot survive removal of one of several supports); keep edited facts as unrelated free text (breaks deletion and correction provenance); use LLM-generated ids as stable identities (not reproducible); keep the narrow mention key and store a merged entity's names in one row (loses which name each passage used, so a split cannot restore it).

### D7. Incremental analysis, review and impact previews

Reuse the small role and existing extraction budgets. Candidate retrieval compares new/changed facts to bounded local candidates by normalized entities, predicate, scope/time and semantic similarity. Ask for structured category and possible-conflict output containing only allowed ids and source spans. Validate spans against the indexed revision, require nonempty evidence, cap counts and string lengths, and reject executable instructions or foreign references. Parser fuzzing covers invalid UTF-8, extreme numbers, cycles, duplicated ids and invented citations.

The analysis response validator accepts only supplied fact and existing-category IDs. Each proposed category cites one exact, uniquely occurring quote from evidence supplied for that fact; each possible conflict cites a quote for each of its two different facts. It bounds the complete response, proposal counts, reasons and quotes, rejects duplicate proposals and foreign IDs, and resolves quotes to byte ranges in the supplied revision text. A quote that does not occur exactly once is rejected rather than assigned to an arbitrary passage. The validator treats reasons and passages as untrusted text, and accepted proposals remain suggestions, not automatic truth or permission changes.

Assign existing categories automatically with an explanation. Suggest new categories for review to avoid taxonomy sprawl; items can be multi-label. Manual labels and rejected assignments take precedence. `policy.knowledge.categorization` and `policy.knowledge.consistency` each default on and require extraction on for model work. All analysis calls share `extraction_daily_calls`; none quietly bypass the gateway or budget. If unavailable, chunk/search first and show pending extraction/checking.

As an interim extraction safeguard, do not dequeue passages when the model rejects the request or returns an invalid extraction. Retain the pending state and apply capped exponential retry backoff, so the reader does not imply that an unchecked Source was assessed or repeatedly spend its analysis budget at a fixed short interval. A permanently invalid batch can delay later extraction until a future bounded batch-splitting and per-item failure queue is implemented; ordinary text search remains available.

Persist a category's display name and a normalized unique name; Uncategorized is a computed view for facts with no accepted assignment, not a deletable category. A manual accept or rejection is a durable locked decision that automatic proposals cannot overwrite. Reset removes that decision, allowing later automatic suggestions. During a merge, retain the destination's manual decision when both sides contain manual decisions; otherwise a manual decision wins over an automatic assignment. If both are automatic, preserve the destination's explanation. Delete and merge remove only category records, never facts or evidence. Category changes increment the knowledge generation and never mutate a publication's selected entries.

The category-store prototype requires an automatic assignment to name an exact excerpt linked to an active support for that fact and to match the graph generation analyzed; it rejects stale writes inside the database transaction. If that support stops being usable, remove the affected automatic assignment even when another independent support keeps the fact available. Manual decisions do not depend on a model excerpt. This storage contract does not itself schedule model analysis, expose the category workspace, or grant sharing access.

The gated evidence binder converts an already validated analysis span into an exact excerpt only while its graph generation still matches, the cited support and revision are current, and the support's saved text matches the current passage. It refuses invalid UTF-8 boundaries and cannot extend a previously exact support to unrelated text. The exact bytes are read from the stored passage and linked to the supporting set in the same transaction; duplicate bindings are idempotent. Category and conflict writes also recheck the excerpt bytes. This remains an isolated storage building block: production revision writers, atomic multi-proposal application, source authorization and analysis scheduling are still required before exposure.

A possible inconsistency is keyed by its two canonical facts, not by model-generated identifiers. Its current candidate records the two exact evidence excerpts and an untrusted explanation. A user decision records those same evidence identities, the choice and its reason in history. If either cited support becomes unavailable, the candidate enters a needs-recheck state and its old decision ceases to resolve the current question; a later evidence-bound candidate reopens it for review. Forgetting either cited excerpt removes dependent candidates and history. This preserves the difference between an unresolved checked disagreement and one awaiting analysis.

The gated schema conservatively supersedes every support referencing a revision when that revision stops being current; new automatic category and review proposals must cite a current revision. This prevents stale evidence being presented as current, and on its own would also invalidate evidence whose passage did not change.

Evidence rows are immutable, so the gated store writer carries unchanged evidence forward instead of editing it. A passage is unchanged when its heading, text and date are identical, wherever it now sits in the item. When an item's content hash or any passage changes, the writer inserts the next revision as not current, copies the evidence of unchanged passages to it, re-points live references (support links, automatic category assignments and both sides of a possible inconsistency) to the copies, moves annotations to the new revision, and only then retires the old revision. The retiring trigger therefore supersedes only supports whose passage was replaced or removed; a fact with another independent support stays available. Re-indexing identical content creates no revision. The old revision keeps its own excerpts as history.

Each extracted finding with a passage is recorded as a canonical fact with a passage-level unverified support, in the same transaction as the legacy relation. A repeated finding from the same passage shares that support; a support that lost its finding to a recheck is revived by the same finding instead of duplicated; a finding without a passage creates no fact. A correction or note is linked as an annotation to the current revision of the item it was stated about.

A finding names one passage, but the model saw every passage of the same extraction request and their dates, and a finding without a stated date takes the passage's date or, failing that, the item's. The gated schema therefore records the inputs of each request: its passages, which request a passage's findings currently come from, and whether one of them took its date from the item. A revision rechecks a retained passage only when one of its recorded inputs was removed or re-dated, when its own date changed, or when it used the item's date and that date changed. Removal and re-dating are handled by triggers on passages, so every deletion path, including forgetting another Source whose passage shared the request, withdraws the affected findings and queues them again in the same transaction. A passage with no record, such as one extracted before the schema or after a failed record write, keeps the earlier conservative rule and is rechecked on any change of its item. Recording is skipped on the production schema.

A support whose passage was replaced stays `superseded` when its legacy finding is deleted with the passage; only a finding withdrawn for recheck on a passage that still exists becomes `unsupported` and can be revived. This keeps revision history distinct from knowledge awaiting analysis. A derivation whose required fact loses its last usable support becomes `unsupported`, transitively, and is not restored when extraction later supports the required fact again from different text: it was derived from the earlier support and must be derived again.

Cascades are bounded in two ways. A derivation chain through required facts may be at most 32 facts long (`kMaxDerivationDepth`); the schema refuses a dependency that would make a longer chain, including by joining two shorter ones, so invalidation and forgetting never approach SQLite's trigger depth. History is bounded to the current revision plus four superseded ones per item (`kRetainedSupersededRevisions`); a fifth older revision is deleted with its excerpts, its superseded supports, review history that cites it, and facts and derivations it alone supported. Four was chosen to let a user compare recent versions without the history of a frequently edited file growing without limit; it is a storage bound, not a promise of a version archive.

Limits that remain: there is no production writer for derived supports yet, so required-fact behavior is verified on stored rows only; a deleted-fact protection is tied to the item version, so a passage that is no longer rechecked keeps the deletion while a later recheck of it may extract the fact again. A revision or removal that touches more than 2,048 passages first withdraws the derived knowledge it will invalidate, 256 passages per transaction, releasing the lock and pausing briefly between steps. For a revision, that is the findings of passages being replaced or re-dated, of passages extracted beside them, and of kept passages that will be rechecked. For a removal, it is all of the item's findings, then its excerpts. The final change of content stays one transaction, so a reader never sees a partly replaced or partly forgotten item, but it no longer writes the passages itself. A change of more than 2,048 passages is staged: the new passages are written beforehand, 256 per transaction, as passages of a hidden staged item keyed by the item and its content hash, with each passage's position. The final transaction checks every staged passage against the content being written, moves matching ones to the item, writes any others normally, and moves the replaced passages to a hidden retired item instead of deleting and unindexing them there. Afterwards the retired passages are deleted 256 per transaction. A replaced passage that still holds findings, or shares an extraction request with current findings, is deleted in the final transaction instead, so its triggers withdraw those findings at once. A large removal retires its passages the same way. Hidden items are not Sources. Full-text search, item search and re-embedding exclude them, and nothing queues them for embedding or extraction. Every other reader reaches a passage through an enabled Source, the item's relations or its mentions, and staged and retired passages have none of those. Staging runs only when the Source is on and the item is not excluded, and the write rechecks both. A stage whose change is not written is discarded, as is a stage of another version of the item. Forgetting an item or a Source retires its stage too and deletes the retired passages before returning. Readers therefore see the previous or the new content in full, with the staged passages already indexed. Leftovers are hidden. The item's next change resumes or discards an interrupted stage. The next change, discard or forget of any item deletes leftover retired passages, and Delete all removes both. Each step leaves a valid state: withdrawn findings await recheck and their passages are queued for extraction again, so if the change never completes (a crash, a refused write, a file that turns out not to be eligible) the unchanged item recovers its findings. A finding withdrawn in advance whose excerpt does not carry over to the new revision is recorded as superseded, the same as one the schema supersedes itself. An exact, model-analyzed support on a removed item is deleted rather than kept awaiting recheck; analysis has to run again if the removal does not complete. Callers that hold the database lock around a revision run the withdrawal and staging before taking it and the cleanup after releasing it. Two costs remain within single transactions. The switch still carries unchanged evidence to the new revision and rewrites the owner of every staged and replaced passage, which is a few hundred milliseconds for 10,000 passages. One withdrawal or excerpt-deletion step can also invalidate or delete a whole derivation graph that depends on its 256 passages. Bounding those needs revision evidence staged before the switch and steps sized by their dependents, not only by passages. With atomic policy and revision fences for analysis writes, these keep the migration gated (tasks 7.6, 7.7, 8.5).

For an item-removal preview, read the item, all its revision evidence, the dependency graph and the generation in one SQLite read snapshot, release the database mutex, then calculate support changes iteratively. Reject a missing, oversized, cyclic or incomplete graph rather than silently reporting a partial count. The current preview is explicitly incomplete because extraction, inconsistency analysis and publication differences have not been incorporated, and its generation still needs to be checked atomically with a future confirmation.

The isolated confirmation prototype stores an opaque, short-lived, one-operation token bound to the item and graph generation, without copying source text. Confirmation explicitly accepts the incomplete analysis and rechecks the generation while holding the deletion transaction; stale, cancelled or expired tokens cannot delete an item. This prototype is not exposed until the source bytes and policy revision are rechecked, existing-share synchronization is serialized, preview presentation and all publication withdrawals are connected, and bounded cascades are enforced.

Explicit imports stage a content-hash snapshot in encrypted temporary knowledge storage, parse and analyze it, then compute a dependency diff. A preview token includes input hashes, knowledge generation, operation and expiry; confirmation rechecks the source bytes, policy and graph revision in a transaction. Cancel cleans staging; expiry/restart cleanup uses the existing data-root protection. Large folder previews paginate and show exact processed/total counts, with `Import for search; finish analysis later` as a deliberate option. They never say analysis is complete when it is not.

Watched changes apply safe indexing automatically and create a Changes entry. Immediately mark obsolete evidence unavailable for current answers, even if extraction is delayed. Detect definite removal separately from a temporary file-access/network error; transient failures show stale/unavailable Source state and do not falsely claim the original was deleted. Manual forget excludes automatic re-ingestion and cascades synchronously through retrieval-visible state, then queues large cleanup. Acknowledgment means no deleted content is queryable, even if encrypted page reclamation happens later under local-storage rules.

As an interim protection in the existing indexer, recheck file metadata and read permission after worker operations and before accepting or discarding their results. A changed or unavailable file retains the previous indexed item with a freshness warning, while a policy denial removes it. Size and modification time are only an interim race detector: changes that preserve both require the content-hash revision mechanism above, and an atomic policy/commit fence remains required.

For the current file indexer, serialize the final eligibility check and item write with the local knowledge database's lock. Recheck that the file is still selected and has no user exclusion at that point, so a forgotten item or removed last import is not restored by an in-flight result. This is limited to the current process and file indexing; the revision-generation fence must also cover every other Source and writer.

As an interim extraction and embedding safeguard, compare the whole input batch with currently stored chunks under the same local lock used to apply model output. If any passage has disappeared or changed, discard that batch's output and leave surviving passages queued for retry. This does not replace durable revision identifiers: a deleted and recreated chunk can reuse an id and identical content.

Recheck local search candidates against the current stored item and chunk after a team search and after reranking. Discard forgotten or changed candidates before sending them to reranking or returning them. This is a current-process snapshot check, not a durable retrieval generation or a recall guarantee when a result is discarded.

Conflict review offers Keep both with scope, Prefer this with a reason, Correct, and Later. Do not call the UI a fact checker or imply that no candidates means no contradictions. A conflict resolution records evidence revision ids, not just fact ids; source changes invalidate its premise. Search tools share a single state filter with UI browse so the agent cannot answer from unsupported knowledge the user sees as removed.

Alternatives: compare every fact against every other fact (quadratic cost); overwrite older facts with newer text (date alone is not authority); block all indexing on model access (breaks offline search); silently accept all model categories and conflicts (unreviewable behavior).

### D8. Reviewed category publications with dependency-based withdrawal

Category Share opens a selection of eligible current facts/notes. Default to the selected entries, not the entire private category. `policy.knowledge.sharing.derived_sources` defaults to `[files, notes]`; administrators can explicitly allow additional Source kinds. Every dependency necessary for the published statement must meet this rule. A fact that independently has a fully permitted support set can use that set only if the generated public statement is wholly justified by it; mixed inference is excluded. The same eligibility engine drives preview, serialized payload and server declared-kind checks.

The preview is the exact serialized public payload: statements, optional approved excerpts and public titles, no local paths or hidden graph metadata. It names the audiences and states `New or changed knowledge waits for your review`. Warn on copied mail/Chat/transcript origin where applicable. The user can deselect content and edit public titles; substantive rewriting creates a new reviewed note with retained dependencies and requires another preview. Excluding evidence from the published payload does not remove its private dependency for lifecycle/eligibility.

Company is an administrator-configured alias for an existing Group, default unset. Use the existing Group picker and explicit allowed Group. The special `everyone` Group can be designated, but the existing wildcard behavior must not silently make it publishable: explicitly permit it through the policy. No second organization-wide authorization mechanism.

Publications get independent ids, versions and entry ids. Category rename, split, merge or removal never broadens publication or destroys underlying knowledge. Removing a fact from a category marks a pending removal from publications created from that category; confirmation of the category edit previews that removal. New category additions never publish automatically. Existing explicit document/folder live shares keep their behavior and are labeled `Source changes shared automatically`, with the precise folder scope visible.

Local changes invalidate affected published entries and enqueue withdrawals before additions. Keep unaffected entries. Safe withdrawal cannot wait for an LLM or an exhausted extraction budget. Offline UI explicitly states pending server removal. Outbox records store minimal remote identity, expected revision, removal generation and retry state, so forgetting content does not delete the only record needed to withdraw it. For Delete all, move only those minimal encrypted records outside the stores being erased and retain them with startup configuration under client/local-storage; a new sign-in by the same user may be needed before retry. Delete them after acknowledgment. Queued retries never contain newly unapproved text. Already delivered chat answers or copies on a recipient's machine are not recalled; the removal confirmation distinguishes future retrieval from copies already made.

The Delete all handoff must bind pending item withdrawals to the IdP issuer, control-plane endpoint and authenticated subject, and persist them in a CurrentUser-protected, atomically replaced file that does not depend on the database keys destroyed by the wipe. The wipe may preserve only that designated file, not arbitrary files from its staging directory. A durable wipe intent is written before sign-out; startup completes an interrupted wipe before opening content stores. Invalid or unreadable pending records fail closed rather than being treated as an empty outbox. Retry only with the matching bound account and endpoint, never with a different account; do not delete an outbox entry until the server acknowledges that removal or confirms it is absent for that same account. Concurrent or delayed uploads need the separate server withdrawal barriers before this workflow can claim full publication safety. Until this handoff is implemented, refuse a whole-profile wipe when an item withdrawal cannot be acknowledged and preserve the existing records.

Derive the cross-process lock name from the resolved parent directory and the designated outbox filename without opening or resolving the replaceable outbox file itself before acquiring the lock. This keeps the lock identity stable across file replacement and avoids a competing pathname-resolution handle preventing an atomic rename. A failed write or replacement must preserve the previous file and return an error rather than discarding queued removals.

The legacy server keys item ownership by mutable username, so a 404 under a subject's new username does not establish that an older username's share is absent. Do not activate subject-bound offline retries or treat that 404 as a successful whole-profile withdrawal until the server has an authoritative, safely migrated subject-to-owner binding and a contract for legacy ambiguous rows. The interim online path records each successful withdrawal before continuing and fails closed for an ambiguous 404.

Alternatives: automatically share every future category member (private data leaks through classification); upload the private graph and enforce access later (violates local-only design); flatten a derived fact into an unrelated note (loses update/delete propagation).

### D9. Server revisions, current authorization and bounded parsing

Add publication endpoints under `/api/v1/knowledge/publications`, separate from existing item PUT semantics. The write body includes `expected_revision`, operation id, public entries/evidence and audiences. Server-computed content hashes, not client hashes alone, decide idempotence. Limits initially reuse 2 MB per item and the existing per-owner quota, with at most 500 entries and 2,000 approved evidence spans per publication. Paginate reads; reject oversize payloads before expensive embedding. Quotas count the serialized text and pending staged work consistently.

`GET /api/v1/knowledge/capabilities` is an authenticated, additive discovery endpoint returning `publication_read_versions` and `publication_mutation_versions` arrays of positive integer schema versions. Initially both arrays are empty: internal prototypes do not constitute support. A missing endpoint has the same meaning for a newer client. Clients ignore additional capability keys and require an explicitly advertised version before submitting a publication mutation. Existing item and search routes do not depend on discovery.

The version-one mutation envelope has exactly `expected_revision`, `operation_id`, `title`, `groups` and `entries`. Each entry has exactly `id`, `text`, `source_kinds` and `evidence`; each optional evidence excerpt has exactly `id`, `title` and `text`. IDs are bounded ASCII tokens, Groups and declared Source kinds are unique within their lists, entry and evidence IDs are unique in their publication, and all strings are valid Unicode without unpaired surrogates. Unknown keys, including local paths and private graph identifiers, are rejected rather than silently forwarded. Check the encoded content size and structural limits before embedding; this shape does not imply that the server can verify the truth of private dependencies. Version/capability negotiation and public citations remain required before exposing this endpoint.

For version one, an ID is 1–200 ASCII letters, digits, dots, colons, underscores or dashes; the expected revision is a nonnegative safe integer. A title is nonblank and at most 300 UTF-16 code units, and entry and excerpt text is nonblank and individually bounded by the configured publication byte limit. There are 1–100 distinct nonblank Group names, each at most 300 UTF-16 code units; 1–500 entries; and at most 2,000 excerpts across the publication. Each entry declares at least one distinct Source kind from `threads`, `files`, `mail`, `calendar`, `meetings`, and `notes`. The complete JSON encoding, including metadata, must fit the configured item byte limit. Empty excerpt lists are allowed. These bounds do not grant Group or Source-kind authorization: both remain subject to current server policy at commit.

Compute embeddings outside the write transaction, then revalidate current authorization, source-kind policy, quota, expected revision and removal generation inside the final transaction. Competing writes return 409, identical operation retries return the committed revision, and failures leave old content intact. Partial withdrawals remove matching chunks/excerpts/vectors synchronously from query-visible tables and write durable per-entry barriers; whole removals block resurrection. An old client cannot bypass these barriers via the old item API because publications occupy a separate typed identity space.

The publication revision ledger keys each publication by the verified issuer, stable subject and publication id. Its current-revision record survives removal as a content-free tombstone, so a delayed create based on revision zero cannot recreate removed content. A committed operation id is bound to a server-computed digest of its exact request and its resulting revision; a repeat with different bytes is a conflict. A matching retry reports both its original committed revision and the current revision, without restoring old content. Partial and whole withdrawals advance the same revision before any later explicit publish; administrator removal also leaves a separate blocked flag until an authorized administrative resolution. The ledger is not an authorization mechanism and must not be exposed before current authorization, quotas, searchable content cleanup and legacy compatibility are connected.

Keep the currently published title, audience, entries, declared kinds and approved excerpts in publication-specific tables beneath that ledger, with cascading deletion of an entry's excerpts. Replace the complete current content inside the same revision transaction; whole removal deletes the title and audience as well as entries. The ledger and operation records retain only identity, ordering and hashes, not removed text. This storage layout alone is not a publication API or an authorized search service: chunks and embeddings must be removed in the same transaction, and quota and authorization must be rechecked before commit.

Publication search chunks are children of their individual entries, with an FTS index maintained by insert/delete triggers and any vector stored on its chunk row. Entry or whole-publication removal cascades through chunks and the FTS index in the same transaction as the revision fence; removing the last entry also removes the title and audience. Test both direct removal and rollback. Chunking uses only reviewed public entry text. This indexing primitive remains inaccessible until the shared authorized-revision relation, ranking, identity refresh and compatible citation contract are complete.

Search and direct reads use one authorized-revision relation before ranking and before returning any metadata. Re-evaluate owner policy with current control-plane Group definitions/assignments and guardrails, rather than `team_owners.permitted` alone. Identity-provider role snapshots follow the expiry/refresh contract of control-plane/identity; expired authority is not treated as current permission. Until a role-derived owner authorization can be refreshed, withhold those publications and show the owner that verification is needed. Server-known membership, policy and deny-list changes invalidate immediately. No SkoWork component issues substitute identities or tokens.

The server can validate declared Source kinds and payload shape but cannot independently verify private source truth. Treat all uploaded text as owner-published untrusted content, never proof of correctness. Removing audit content does not remove audit accountability: keep actor, ids, revision, audience, outcome and bounded removal reason. The admin inspector can see only published payloads, never hidden Source paths or unpublished categories.

Alternatives: last-write-wins uploads (resurrect withdrawals); rely only on client checks (bypassable); trust indefinitely cached owner permissions (revocation delay); introduce a general synchronized graph service (outside architecture and scope).

### D10. Performance and evidence gates

## Risks / Trade-offs

- [An inferred conflict or category is wrong] -> Keep evidence and scope visible, label suggestions, preserve manual choices and allow defer/reversal; evaluate multilingual cases before enabling bulk analysis.
- [Derived knowledge accidentally contains restricted source material] -> Traverse full dependencies for eligibility, generate the exact preview payload, require explicit publication, and test mixed-source adversarial cases.
- [Source deletion loses its pending remote cleanup] -> Persist withdrawal identities separately from content and retry with removal barriers; clearly label offline pending removal.
- [Reprocessing recreates rejected or forgotten content] -> Preserve minimal version tombstones and import exclusions; fence jobs by source generation and recheck before committing.
- [Compaction loses user requirements or upgrades injected text] -> Coverage ledger, bounded full-range summaries, independent trusted state, adversarial tests and seeded real-model recall checks.
- [Summarization itself exceeds model or daily budgets] -> Bound each pass against the small role, persist progress, use normal gateway budgets and give a recoverable context error without oversized calls.
- [An old client or delayed write restores removed shares] -> Typed publication ids, expected revisions, durable removal barriers and minimum-capability checks for mutation.
- [An owner is offline and role-derived authorization expires] -> Withhold unverifiable access rather than extend stale authority; show the verification state and resume once central identity permits it.
- [A large speech package fails behind the organization proxy] -> Use the existing proxy-aware transport, authenticated mirrors, cancellation/retry and offline import; verify the actual published layout.
- [New UI becomes more complicated than the current one] -> Four task-oriented sections, readable facts and evidence first, progressive disclosure, records before dialogs and keyboard-accessible pickers.
- [Unfinished older deltas conflict at archive] -> Verify the composed baseline and header/scenario preservation in a temporary OpenSpec workspace, sync only approved prerequisite requirements, and archive this change last.
