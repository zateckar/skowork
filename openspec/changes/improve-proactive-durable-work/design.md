# Design

## Context

See proposal.md. `client/src/scheduler/mail_sources.cpp` feeds source events into `Scheduler::source_event`; mail sync is in `client/src/mail/`. `RunStore::recover()` in `client/src/runtime/run_store.cpp` fails running Runs on startup, and the scheduler retries failed Occurrences. The runtime already stores Tool results and supports Child Runs and persisted interrupts. The inbox and native feed are in `client/src/inbox/` and `client/src/shell/`. These observations are not evidence of production qualification.

## Goals / Non-Goals

**Goals:** Use existing client-owned storage and model gateway; make triage reviewable; avoid blind effect replay; expose meaningful progress.

**Non-Goals:** Replace the scheduler or change its catch-up policy, resume a process image, guarantee exactly-once external effects, or broaden Tool authority. The existing shutdown-failure state remains; continuation is user initiated.

## Decisions

### D1. Independent triage subscription

Add a client/event-triage component that consumes eligible mail/calendar sync changes before scheduler Trigger matching. The current mail listener is in-memory and some exclusion paths remove records without an event; it is not a durable subscription. Change mail sync so each page's source mutations, triage records and resumable source position commit together in encrypted `app.db`. If the page would exceed triage capacity, atomically persist a gap marker and pause triage for that scope while source sync and other consumers continue. The user sees that suggestions may have been missed; after acknowledgement and freed capacity, establish a fresh baseline before processing subsequent changes. If Graph cannot resume the saved position, perform a bounded full resync, reconcile by stable item/revision identity and explicitly report an unrecoverable gap. Spike 1.1 must demonstrate these properties before implementation proceeds.

Persist account/source/item/revision identities, state and bounded tombstones, not a second full mailbox. On first enable, establish a source sync baseline without creating historical suggestions, then process changes after the baseline; display the completed baseline time so the user can see the monitoring start. Changes incorporated during initial baseline are historical for triage. An event remains pending until its result and suggestion are committed atomically; a crash may repeat a model request, but cannot create a duplicate suggestion. Debounce by item, gather up to 20 events for up to 30 seconds, and respect the 60-second request interval in D5. The user owns selection, responsibilities and enablement. Disabling invalidates in-flight results and stops new requests; it cannot retract data already dispatched. Deletion, exclusions, policy changes and access revocation invalidate revisions and withdraw derived previews/reasons even if sync emits no deletion event. Transient offline status alone does not imply revocation. Existing mail restrictions are rechecked before dispatch, result commit, display and starting a Run.

Alternative: treat each source event as a scheduler Trigger. Rejected because a Trigger starts a Run and triage is a suggestion, not a Run. Alternative: maintain an independent full channel history. Rejected because it duplicates sensitive source data and retention rules.

Spike evidence so far: the Graph mock exposes `changeKey` derived from its sequence for both messages and events, and the parser reads it. A mock folder move gives a message a new ID and tombstones the old ID; the current Graph client does not request immutable IDs, so cross-folder identity cannot be assumed. The current sync writes each source item and calls in-memory listeners before storing the final delta link; it does not commit a page, subscriber intake and cursor atomically. A listener failure is not replayed to that listener after restart. These observations do not yet establish page-atomic intake, overflow behavior, immutable source identity or the full resync contract, so spike 1.1 remains open.

The current `MailStore` item methods start their own transactions but discard their transaction status, and `set_delta_link` discards its write status. Simply wrapping existing calls in a page transaction therefore cannot prove atomicity or fail closed on storage errors. The spike must establish transaction ownership and propagate every source, intake, gap and cursor write failure before a page can be acknowledged.

An isolated encrypted-database characterization now reproduces the concrete failure: an outer transaction can commit an advanced delta cursor while `upsert_message` reports a creation whose nested transaction did not write the message. A test-only page prototype rolls back source, pending and cursor rows on an injected error or actual child-process termination after each write; termination immediately after commit retains all three rows, and replay leaves one pending row. This uses synthetic fixed rows, not the production mail store or suggestion lifecycle. It does not demonstrate atomic Graph intake, full resync, overflow or suggestion deduplication, and therefore does not complete spike 1.1 or establish production safety.

A second test-only prototype consumes real Graph-mock mail pages into separate encrypted test tables. It accepts exactly 1,000 pending revisions, does not mistake replay for overflow, rolls back a page on an injected cursor-write failure, and atomically records a gap when the next page exceeds capacity. After reopening the profile, another page advances the prototype source and cursor while the gap remains and pending count stays at 1,000. Another test exercises a mock mail edit and tombstone, duplicate suggestion completion and late results: the old suggestion is removed, an obsolete result cannot restore it, and a stale source cursor cannot reintroduce the item. These are test tables, not actual Threads.

An expired-cursor resync experiment marks observed source rows in place and stores its page cursor in encrypted test tables, resumes after a profile reopen, retains unchanged suggestions and reconciles missing items only on the final page. The marker adds one fixed-size flag per stored source row instead of a separate growing set of observed IDs. Ordinary page intake checks the resync state inside its transaction and is rejected during the scan, including after restart. An injected final cursor-write failure rolls back that final deletion sweep, and an item arriving during the lost interval is treated as baseline while the gap remains recorded. This is a single-scope experiment: it has not established bounded tombstone retention, provider page-size or real Graph identity and ordering behavior. The gap is only a database record: there is no user-visible warning, acknowledged baseline, production store integration or process kill of this Graph prototype. Those remain necessary before completing spike 1.1.

Opaque source revisions cannot be ordered lexically. If a page contains conflicting revisions or a live item and tombstone for one identity without a defensible ordering, fail the page without advancing its cursor instead of selecting a winner. A test-only prototype rejects conflicting revisions before any write; this does not qualify provider ordering or cross-folder identity. Source-provider semantics and reconciliation must be verified before production intake.

The mock previously recomputed a mutable collection for every offset. A disposable Graph-mock test confirmed that deleting an already-read message during a full sync shifted the next offset and permanently omitted an unchanged message, including from the next delta. The mock now retains a stable response snapshot for each paged mail and calendar delta sequence, with later mutations reported in a subsequent delta; targeted mail deletion and calendar edit tests, the full mock suite, and native mail tests pass. A separate native test confirms an unchanged next link survives a client reopen and that an expired link returns `sync_state_not_found`. This mock behavior is a test contract, not a claim about Graph's snapshot guarantees; real Graph acceptance must independently exercise its documented delta semantics. It does not demonstrate page-atomic production intake, overflow or suggestion deduplication.

Microsoft documents an opt-in immutable ID for Outlook messages and events, including delta responses, but it must be requested on each relevant request and is stable only within the same mailbox; archive-mailbox moves and export/reimport can change it. Existing stored IDs would need translation or a deliberately visible fresh baseline, and a folder delta removal may indicate a move rather than deletion. See https://learn.microsoft.com/en-us/graph/outlook-immutable-id and https://learn.microsoft.com/en-us/graph/api/message-delta. This is a candidate for the spike, not evidence that the current mock, sync, deletion handling or migration supports it.

### D2. Decision and presentation

Use the gateway's `small` model role, no tools, strict bounded structured response, one outcome per event: relevant, not relevant, or uncertain. If the role is unavailable, retain pending events and show triage unavailable; do not bypass the gateway or switch roles silently. Uncertain produces no suggestion and remains visible in a triage diagnostic count, not a silent claim of irrelevance. Validate exact event IDs, revision, schema and bounds; malformed output or a failed request retains the batch with capped backoff. User responsibilities and event text remain data, not instructions; user-provided responsibilities guide classification but cannot change policy. Create a system-origin Thread for a relevant item, with no Action item unless an existing Question is raised; show it in Unread using a dedicated suggestion status, not in Action. Explicit Start atomically claims the current revision and records the user's request as a visible user message, creating an ordinary user-origin Run with untrusted source provenance; simultaneous starts cannot create two Runs. Dismissal suppresses that revision; a later revision may create a new suggestion. Once work starts, a subsequent source change does not rewrite user-authored or already-executed history; source-derived suggestion content is removed under source deletion/exclusion rules and downstream retention remains owned by local-storage. No cross-item aggregation in the first version.

Alternative: local classifier or unrestricted model agent. Rejected because local ML is reserved for speech and the agent would add cost and authority. Alternative: launch unattended Runs automatically. Rejected for the initial scope.

Classifier request and response contract: a batch has 1–20 distinct opaque event IDs and nonempty revisions, each at most 512 UTF-8 bytes. Responsibilities are at most 4,096 bytes and each event's source text at most 8,192 bytes. The request sends these values as JSON data in a user message beneath a fixed system instruction; it uses the `small` role, no Tools and no streaming. It requests a single gateway attempt, with no hidden transport retry, post-401 resend or Tool-call repair; its caller enforces the interval and backoff for any later attempt. A complete response is one JSON object containing only `results`, an array with exactly one object for each supplied ID and revision. Each object contains only `id`, `revision`, `outcome` (`relevant`, `not_relevant`, or `uncertain`) and `reason` (a string of at most 512 bytes; nonempty for `relevant`). Reject unknown fields, duplicate or missing events, changed revisions, malformed types, oversized responses over 65,536 bytes, Tool calls and incomplete completions as an entire failed batch. Do not log source text, model output or secrets on failure. No rejection marks any event processed. This parser and gateway-call boundary can be tested independently, but no source intake or automatic classification is enabled until spike 1.1 is satisfied.

### D3. Recovery with a durable effect ledger

Keep current `failed: interrupted by shutdown` semantics. Create a new top-level Run linked to the failed Run, preserving its immutable history and reconstructing a complete protocol-valid model context at a recorded boundary, including provenance, attachments and compaction state. A transaction claims the failed Run and creates at most one continuation; retries or a crash do not create a second one. Keep the origin and Unattended classification of an Occurrence's Run and carry forward consumed model/tool/time budgets, so continuation cannot reset limits or bypass unattended policy. Re-evaluate policy and Run start gates. Resume only a complete recorded model response; discard partial output. Incomplete or incompatible history disables continuation.

Persist a stable logical operation id and final approved arguments before dispatch, then record completion and result durably. Record intent, approval resolution and dispatch state atomically at their respective boundaries, and fail closed on storage failure. Inspect all parallel calls and the entire Child Run subtree: no continuation or Occurrence retry can begin until every possibly dispatched call is accounted for. Classify uncertain effects on timeouts and failed responses during ordinary execution as well as shutdown; prevent the existing retry path from escaping the guard in each case. A registry describes each Tool's recovery capability: demonstrably read-only/replay-safe, reconcilable by a provider-supported operation id, or unknown. Default is unknown, including arbitrary shell, computer, browser, MCP and connector calls. Reconciliation is read-only, returns confirmed success, confirmed absence only with authoritative evidence, or unknown, and never performs the original effect. A timeout or inconclusive search is unknown. Mail send defaults to unknown unless a provider-backed test proves reconciliation.

The current API connector reports a request-layer failure as though the call was not made. A lost response can occur after dispatch; change that explanation and its structured outcome to communicate uncertainty unless there is positive evidence that dispatch did not happen. The ledger must consume that distinction rather than treating the error text or a generic failed result as proof of absence.

When any effect is unknown after shutdown, create a durable standalone client-raised Question in the existing Thread before any continuation model call. If the Run is still live, interrupt it with the existing client-raised Question mechanism before another model call. Offer stop or continue with unknown; the resolution does not assert whether an effect occurred and does not authorize a resend. Acknowledge each unknown call separately. While any outcome remains unknown, every subsequent Tool call except one explicitly registered as read-only/replay-safe requires explicit user authorization as well as its normal policy decision and any Approval. A single explicit Approval of the exact final call may satisfy both user authorizations; a policy allow alone cannot. This conservative guard covers changed arguments or different tools; a canonical-argument comparison alone cannot detect equivalent effects. The guard and resolutions persist across further crashes and child delegation. Never auto-resend. For legacy histories lacking a ledger, classify potentially dispatched calls as unknown; do not offer an unguarded normal retry or new Run as a recovery shortcut.

Coordinate runtime recovery and scheduler startup so the ledger is classified before any Occurrence can retry. An Occurrence awaiting a choice about an unknown effect remains running and associated with the failed Run without a slot or lease-driven retry. The user can choose to continue despite the outcome still being unknown: claiming continuation atomically binds it to the same Occurrence, retains attempt accounting and ensures only one final transition and notification; it reacquires an unattended slot. Its unknown-effect guard remains active and a failed continuation is terminal for the Occurrence, never an automatic retry. Origin lookup must distinguish the linked continuation from the original attempt and cannot adopt it as a new occurrence or violate origin uniqueness. Serialize issuer cancellation, user stop and revocation against continuation claim and each dispatch: once cancellation commits no new dispatch begins, but an already dispatched external call cannot be assumed undone and remains subject to unknown-effect handling. Runs that fail without an ambiguous effect retain the existing retry policy. Interrupted Approvals remain unchanged. The scheduler delta belongs to this change and is applied after its prerequisite is archived; no prerequisite is silently changed ahead of implementation.

Alternative: automatically replay every incomplete call. Rejected because the effect may already have occurred. Alternative: resume every running Run at startup. Rejected to retain the current Run lifecycle and require explicit user control. Alternative: always retry an Occurrence. Rejected for ambiguous effects.

Spike evidence so far: mail registers search/read and effectful draft, send, move, delete and calendar operations; browser and computer register both observation and interaction operations. MCP and API connector Tool definitions are generated from external configuration, so their effects cannot be inferred from a fixed name. Runtime delegation can start Child Runs, and parallel Tool calls can overlap. Existing retry characterization shows that a later model response can request an equivalent call after an earlier attempt. These observations do not establish replay safety or provider reconciliation for any Tool; all remain unknown until separately justified. A process-termination test of parallel external calls remains open.

The runtime recovery spike now terminates a separate test process after a harmless external file effect and before the Tool returns. Its encrypted Run contains the decision but no Tool result; recovery marks it failed after shutdown, while the effect exists. This proves the outcome is unconfirmed from the Run record, not that a real provider supports reconciliation. A separate injected database failure demonstrates that the current runtime dispatches even when writing the `tool_call` decision fails; the future ledger must treat failed persistence as a dispatch blocker, including in parallel and Child Runs. A parallel test also observes that a completed call's result remains unrecorded until the other call finishes, so a crash can leave a completed effect unconfirmed while the batch is still active. The existing retry path can request a fresh equivalent call, so it must be included in the unknown-effect guard. These are characterizations of the current unsafe paths, not implemented recovery protections.

A second terminated-process experiment delegates the harmless file effect to a Child Run. The child's decision exists without its result, the parent contains the child link without a delegation result, and both Runs fail as interrupted on recovery while the external effect remains. This demonstrates why the recovery assessment must traverse the child history; it does not qualify provider reconciliation or implement a guard.

Registration audit: Graph mail and calendar register read operations as well as draft, send, move, delete, create and respond operations. Browser registers observation and navigation, input, tab and script operations; computer registers observation and desktop input and launch; `shell.run` executes arbitrary PowerShell. File Tools include reads and writes. MCP Tools are generated from server offerings and API connector Tools from administrator-configured operations; their declared policy risk does not prove a replay or reconciliation capability. `delegate` creates a Child Run, and parallel batches dispatch multiple calls before their results are recorded. Default all of these to unknown until a specific implementation has evidence for a more permissive recovery capability; this audit does not certify any Tool as safe.

Recovery capability map for the current registration families (this is a conservative spike result, not an implemented registry):

- `mail.*` and `calendar.*`: search, read, list, get and free-time calls observe source data; draft, send, move, delete, create and respond can change Graph state or notify people. All default to unknown; no Graph operation-id reconciliation or send idempotency has been demonstrated.
- `browser.*` and `computer.*`: snapshots and observations read state, while navigation, tabs, script, input and launch may have external effects. Parameter-dependent policy risk is not proof of replay safety. All default to unknown and have no qualified reconciler.
- `files.*`, `shell.run`, `web.fetch` and `image.generate`: file Tools read or change local data; a shell command is arbitrary; a web request or image generation can contact a remote provider. All default to unknown; no provider or filesystem reconciler is qualified by this spike.
- `tasks.*`, `knowledge.*`, `apps.*` and `skills.save`: these include both queries and operations that mutate local state, launch work or publish a Skill. All default to unknown; no replay-safe or reconciliation capability is inferred from a Tool name or policy risk.
- MCP and API connector Tools are registered from external configuration and may change independently of the client. Their effects and reconciliation are unknown by default, including Tools presented as reads.
- Runtime `find_tools`, `read_attachment` and `ask_user` have internal discovery, data-access or durable-interrupt semantics and need explicit treatment by the recovery implementation. `delegate` and `use_skill` create Child Runs, so account for the whole descendant tree and each parallel call independently; do not treat the parent delegation result as evidence about a child's external effect.

### D4. Progress and control

Emit compact Run and Child Run state transitions and a sanitized activity descriptor from the runtime; project them into the existing Thread feed and Running/Action views. Do not persist raw command lines, output, credentials or model reasoning merely for progress. The parent remains the owner of child cancellation and interrupts. Reuse queue and steering semantics, label pending delivery, and use existing accessibility patterns. Persist transition events; derive current activity from live state and show last known state after restart.

Use only the fixed progress phases `model`, `tools` and `idle`, together with the bounded active Tool count. Emit `model` immediately before a model call and clear it after the call returns; Tool execution publishes `tools` while at least one call is active, otherwise `idle`. Never derive a progress phase or display label from Tool names, arguments, output, activity text or model output. The Thread and Child Run rail localize these fixed codes; a missing or unknown code falls back to the existing generic working state. Terminal and interrupted Run states take precedence over an old progress event after restart.

The Running and Action lists reuse the same fixed localized phase for the active top-level Run, including in the row's accessible name; a pending Action remains separately identifiable. List entries contain only the phase and bounded count, never the underlying progress payload. A progress event refreshes the affected entry, and a fresh list reconstructs it from the latest persisted progress of a currently running top-level Run.

Alternative: stream raw tool output into the Inbox. Rejected for privacy, accessibility and volume. Alternative: create a separate dashboard. Rejected because Thread and Inbox already own this concern.

### D5. Resource limits and validation

On the baseline Windows 11 i5/16 GB machine, target no more than 5 MB additional idle private memory and no periodic model calls while triage is disabled; do not exceed the existing desktop-host footprint budgets. Cap pending triage events at 1,000; overflow records a visible gap instead of blocking normal source sync. After 30 days expire a pending event with a visible count and without claiming it was evaluated. Retain deduplication tombstones until the corresponding cursor can no longer replay the revision; if that cannot be proven within a bounded retention, establish a fresh baseline with a visible gap. Use at most one concurrent triage request and a 60-second minimum interval between request starts; existing gateway and background limits apply. Measure the targets before release. Alternative: unbounded event history and per-event calls. Rejected for storage and budget pressure.

## Risks / Trade-offs

- [False negatives or model hallucinations] -> Show source and reason, keep uncertain separate, test a representative labelled corpus and never use classification as authority.
- [Source deletion or revoked access leaks stored previews] -> Remove previews on revocation/deletion and verify source eligibility again before display or work.
- [An effect is duplicated during recovery] -> Default unknown, durable operation ids, no blind replay, fault injection at each persistence boundary.
- [An older binary retries an unknown effect] -> Treat downgrade as unsafe until a tested database compatibility/version gate prevents the older binary opening the upgraded profile; if no enforceable gate exists, block recovery rollout rather than claiming downgrade safety. Verify on a disposable profile with the actual previous binary.
- [Event storms consume resources] -> Coalesce revisions, bound queue and requests, respect background deferral and show backpressure.
- [Progress leaks sensitive content] -> Store only bounded sanitized descriptors and test secrets do not appear in progress.

## Migration Plan

Add versioned local tables with triage disabled by default and classify legacy in-flight calls as unknown. Existing failed Runs remain readable; offer continuation only where their recorded history is sufficient. Verify a version gate prevents older clients from opening an upgraded profile before rollout; do not assume additive tables make downgrade safe. Restore from a pre-upgrade backup only through existing profile recovery procedures and warn that subsequent data would be lost. Disable feature exposure if migration, compatibility or integrity checks fail; do not delete original Run history.

### Compatibility investigation

The current app opens `app.db` via `open_and_migrate` without requesting its optional newer-version refusal. A disposable-profile test launched the existing local desktop executable with an additive, higher-version prototype schema and observed writable storage with no storage error. This demonstrates that a version bump alone is not a gate; it does not establish the identity or behavior of a previously released binary. The knowledge database has a write-trigger barrier, but that mechanism alone does not prove an older app cannot read the database or dispatch an external effect before a blocked write. A candidate profile migration must demonstrate that the actual previous app cannot open the upgraded profile and dispatch or retry work; a unit test or a version number is not sufficient evidence. Until that demonstration succeeds, recovery remains unreleasable and the compatibility spike is incomplete.

Release builds omit the development-only command-line overrides for the data root, named pipe, machine configuration and registration. Do not launch a release binary with those flags expecting isolation. Run the previous-release test in a separate disposable Windows user profile or VM with an isolated registry, data root and controlled network; create the encrypted prototype under that same user identity. Verify isolation before startup, and never point a release test at the developer's profile or registration.

### Downgrade gate (task 1.4, decided 2026-11-19)

The gate is cryptographic rather than a version check, so a prior client cannot ignore it. Every client so far, including v0.1.0, reads the `app.db` key from `keys.bin` under the name `app.db` with `get_or_create`. It opens the database with that key and checks the schema. A wrong key fails with `not_a_database`. The app then records a storage error and keeps only the tray running, without Runs, the scheduler or Tools. Before its first migration, a client with recovery moves the existing key from `app.db` to `app.db#2` in one atomic `keys.bin` replacement, and from then on uses only `app.db#2`. The database file and its encryption are unchanged, so no data is rewritten. A prior client that starts on that profile finds no `app.db` key and creates a new random one. That key cannot open the database, so the prior client cannot read Runs or dispatch or retry work. When the new client starts again, it removes the stray `app.db` key before it opens the database. A failure to move or remove the key stops the start with a storage error, before any migration. Any later change that makes downgrade unsafe moves the key to the next name.

Verification runs the actual v0.1.0 source as a development build. Development builds honour `--data-root`, `--pipe-name`, `--no-register` and `--config`, so the run uses a disposable data root under the test's temporary folder, a private pipe and no registration. The configuration points at an unreachable control plane, and the unsigned build cannot open outbound connections on the workstation anyway. A run of the signed v0.1.0 release binary in a separate Windows user or VM is not possible on the development workstation. It moves to verify-foundations-on-target together with the baseline-machine measurements of task 5.2.
