# Design

## Context

The native Thread feed folds stored and live Run events into rows, updates streaming assistant Markdown, and uses the same Markdown renderer in human Chat messages. The parser already recognizes fenced blocks and Markdown tables. `ask_user` currently interrupts a Run with a Question containing a prompt, up to eight suggested strings and a free-text answer; it is not a form protocol. See the proposal and delta specs for the desired behavior.

The UI is Win32/Direct2D, with no embedded web engine. The client has a retained element tree, buttons, checkboxes, rich-edit fields and UI Automation. Charts, diagram layout, data-grid interactions, and structured Questions need new work. Run persistence and policy already have separate owners; a surface cannot grant tool permissions.

## Goals / Non-Goals

**Goals:** Use the Thread feed for task-shaped answers; retain the existing message and Question workflows; make actions reviewable, durable and accessible; keep the contract useful with existing gateway models.

**Non-Goals:** Implement a general browser or execute model code; claim A2UI compliance; add new policy decisions; promise that generated data is correct merely because it is visualized.

## Decisions

### D1. Validated, declarative native surface

An assistant message can carry a complete `skowork-ui` fenced JSON block with a schema version, surface identifier, a component tree and plain-text summary. A finite catalog maps data to native widgets, without expressions, scripts, URLs, arbitrary styles, hidden values or remote fetches. It supports sections/cards and read-only text; table, bar and line charts, directed diagrams; and the controls in the spec. Tables support local sort and filter; charts expose their data and units; diagrams expose labeled nodes and edges. Values and labels are literal data; dependencies between arbitrary controls or formulas are not in this version. The surrounding answer remains usable without the surface.

Only the Thread feed's authenticated assistant-message event path may opt into surface rendering; the shared Markdown renderer has no global surface activation. The fence must be a top-level assistant-authored block, not a quoted example. A surface becomes interactive only once its complete, closed block is validated in a durable assistant Run event; unfinished, failed or malformed blocks stay readable as source text. The client may continue to stream surrounding prose. The model is instructed not to use the fence for examples; a plain code fence can show the syntax.

The stored assistant event records whether the model call ended normally (`stop` or `tool_calls`); streamed deltas, failed/cancelled calls, length-truncated calls and older events lacking this marker are not eligible for activation. An earlier successfully completed assistant event remains distinguishable from a later cancelled model call in the same Run. Discovery is conservative: opening fences start at the left margin with the exact `skowork-ui` info string and require a matching explicit closing fence; other syntax remains readable Markdown fallback. To bound repeated Markdown context checks, messages larger than 1 MiB or containing more than 16 candidate surface fences use fallback rather than activating any surfaces.

When the feature is enabled, retain up to 1 MiB of streamed response text for the current model attempt. Clear that buffer when a retry discards the attempt. On cancellation or a terminal model failure, persist any retained text as an `incomplete_message` Run event, display it as ordinary Markdown fallback, and exclude it from the model's conversation history. A separate event kind cannot satisfy the completed-assistant activation check, even if the stream happened to contain a closed surface fence. Mark a capped buffer as truncated; do not silently present it as a complete answer. Successful responses continue to use the existing completed message event.

Limits for v1: 64 KiB UTF-8 per block, nesting depth 8, 100 components, 40 interactive controls, 500 table rows, 20 columns, 500 points per chart, and 100 nodes plus 200 edges per diagram. Duplicate IDs, invalid option/default values, inconsistent data shapes, non-finite numbers, unknown fields, versions and component types fail closed. Strings, labels and references are length-bounded within the total size. The parser rejects excessive input before expensive layout. Citation IDs are resolved against the answer's existing Citation registry; unknown references are shown as unverified text, never as a source link.

The v1 wire contract uses the root and component shapes exercised in `spike.mjs`. IDs are nonempty ASCII letters, digits, underscores or hyphens, at most 64 bytes; display strings are at most 4096 UTF-8 bytes. A component, chart point, diagram node or edge may additionally have `citations`, an array of at most 20 Citation IDs. A table cell may be either a display string or `{ "text": "...", "citations": ["..."] }` so a Citation can be attached to a particular value. Citation IDs encode the existing answer Citation numbers as decimal strings; unknown numbers remain unverified rather than causing the surface to invent a source. A select may specify `value` as one option; a multiselect may specify `value` as an array of unique options. Missing selection values mean no selection. Option labels must be unique. Fields not described here or in the spike shapes are invalid. A preflight JSON nesting limit of 24 containers bounds parsing independently of the eight-level component limit.

**Alternatives:** Render generated HTML/JS inline (conflicts with the native architecture and increases the trust surface); add a model tool for each surface (complicates sequencing and portability); implement A2UI immediately (a useful future interoperation target, but requires a native renderer and a complete compatibility decision). Inspect A2UI and dsh-genui during the spike, without presenting this contract as either protocol.

**Protocol comparison (2026-11-14):** [A2UI v1.0](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md) streams surface creation, component and data updates as separate protocol messages and supports typed function calls. Its [basic catalog](https://a2ui.org/concepts/catalogs/) has cards, buttons, text fields, checkboxes, choice pickers and sliders, but tables, charts and diagrams would need custom catalog components. Adopting it would additionally require a native C++ protocol engine, catalog negotiation and a decision about its data-binding and function semantics. [dsh-genui](https://github.com/omdsh-dev/dsh-genui) already uses an inline JSON fence, tables, charts and form actions, with local sorting/filtering and a browser-oriented renderer; it supports incremental rendering and a larger catalog, including expressions and external media, which this change does not adopt. Both support the catalog concept, but neither eliminates the required native implementation or SkoWork's Run/Question and approval integration.

The v1 SkoWork catalog covers all proposed presentation families: sections/cards and labels; tables, bar/line charts and directed diagrams; buttons, single/multiple choices, switches, text and sliders. Table sorting/filtering and section expansion are local; explicit submission is host-bound as in D2. Untrusted incomplete surfaces stay inactive as specified, rather than inheriting dsh-genui's progressive interactive mounting. The trade-off is reduced interoperability and flexibility in exchange for a smaller first contract that fits the existing Thread event stream. This decision remains subject to the model and native-rendering spikes.

### D2. Explicit, host-bound action routes

An answer surface can only submit a user-visible intent and the values of its labeled fields as a user message in its Thread. It is not a tool invocation. When the Thread has another active Run, reuse the composer's explicit queue/steer choice; do not silently steer. A surface in an incomplete or cancelled assistant message is not actionable.

Structured Questions are a separate host-created route: extend `ask_user` with an optional validated form description. The runtime assigns and persists the Question Action item and its surface identity and revision; the model cannot select an Action item ID or Approval ID. The Question card renders the same catalog's applicable form controls and retains the existing free-text response. Submit resolves only that pending Question and returns the validated visible values as the asking tool's result. A generated control never resolves an Approval; subsequent tool calls use client/policy-enforcement and its existing approval presentation.

When enabled, `ask_user` accepts an optional `form` containing a complete v1 surface with exactly one submit button. Invalid or multiple-button forms fail the Tool call rather than producing active controls; omitting the form preserves existing behavior. The host persists the validated form, its content-derived revision and an unpredictable submission token on the created Question. The structured response must match the host-owned Thread, Run, Question, revision and token; resolving the Question and recording the resolution event are one transaction, and a retry with the same token returns the accepted outcome without resuming again. Keep free-text responses and the normal parent/Child Run resumption path.

The user can review the action label and selected field labels and values before submission; submission contains only fields actually displayed and enabled, with validation against their declared type and options. No generated hidden fields, paths, tool arguments or approval flags are accepted as authority. Labels and model-produced descriptions remain untrusted; generated UI cannot imitate native Approval cards or claim policy authorization.

For v1, the native review and host submission reject an action while any enclosing section containing a field or the submitted button is collapsed. The UI sends its current section expansion state to the UI-only host route, which validates the section IDs and requires those sections to be expanded before accepting values. The user can expand them and review again. This avoids including values from collapsed controls without silently changing the user's exploration state.

**Alternatives:** Let a button directly invoke an RPC or tool (bypasses the agent and approval boundaries); infer the pending Question from a nearby arbitrary fence (ambiguous and vulnerable to stale/cross-Run actions); auto-submit on field changes (surprising and expensive).

### D3. Identity, streaming and durable state

For an assistant surface, the host binds identity to Thread ID, Run ID, stored assistant event sequence, block index and a content-derived revision; for a Question it additionally binds the host-owned Action item ID. IDs produced by the model only identify controls inside that binding. Draft values, selection, filter and sort state live in the user's existing encrypted local storage, keyed by that identity, and are deleted with the Thread. Preserve an unchanged surface's state when the feed refolds or streams; discard incompatible old drafts when a revision changes and show the old surface as unavailable.

Within a client session, serialize saves for each bound surface and coalesce pending edits to their newest state. Keep the latest local snapshot across Thread navigation while a save is outstanding, so reopening a surface cannot replace a newer edit with an older database read. A failed save leaves the latest draft available for retry and is reported to the user. The shutdown path must finish or explicitly report outstanding writes before claiming durable state.

Ordinary window close and application quit use the same localized warning when a draft is pending or needs retry. Cancelling application quit leaves the host running. When Windows asks whether the session may end while such a draft exists, veto that attempt and show the window-close warning, allowing the user to keep working or explicitly close and retry shutdown. A forced session termination or process kill can prevent any asynchronous save or prompt; it cannot be represented as a successful durable save.

An action has a host-generated idempotency key. Validate its binding, revision, status, displayed values and current Run/Question state at the host, not just in the widget. Atomically persist submission acceptance with the Question resolution or user-message enqueue/Run creation, under a uniqueness constraint; retry returns the accepted outcome. If offline or storage fails, keep the draft and show a retryable error, without pretending submission succeeded. A pending Question remains pending across restart; resolved, cancelled, superseded or deleted targets reject stale actions. Do not claim exactly-once external side effects: downstream tools retain their existing semantics.

An answer surface permits one accepted submission for its bound revision, even when it has several buttons. Button-specific tickets identify a retry of the selected action; an additional surface-scoped acceptance record is written in the same transaction as enqueue. A retry of the accepted button returns the original outcome, while another button is rejected. Opening a submitted surface reports this persisted status so all of its actions remain disabled after refold or restart.

**Alternatives:** UI memory alone (loses drafts and duplicate protection on restart); model-provided IDs alone (cross-Thread collisions and spoofing); replay the raw JSON to the model on each UI update (unnecessary context and confusion between generated data and user input).

### D4. Model and citation integration

Advertise the small v1 catalog and examples in the Run instructions only where the Thread client supports it. Continue using the existing gateway and streaming response; do not assume provider-specific structured-output support. Assistant prose and actual submitted user responses remain in conversation history; local-only sorting and filtering do not. The submission identifies the user's selected labels and values, without replaying an entire surface. Extend Citation discovery to inspect validated structured content rather than assuming references inside a code fence are found by the prose scanner. Surface references cannot create new Citation records.

**Alternatives:** Force every response through a structured-output mode (provider compatibility and inappropriate visual responses); send all interactions to the model (latency and unnecessary calls); expose unverified model-supplied source links (misleading evidence).

### D5. Spike, acceptance budgets and rollout

Before implementation, run a reproducible local spike with the configured organization gateway and representative comparison, planning, decision and data-exploration prompts. Record model and configuration, prompts, surface validity, quality, response latency and accessibility findings without recording secrets or sensitive user data. Target at least 90% schema-valid completed surfaces over 40 prompts spanning at least two available model configurations; record the sample and failures, not a statistical guarantee. If two configurations are not available or the target fails, stop the implementation and resolve the result in the change before expanding scope.

**Model spike (2026-11-14):** The local in-memory SkoWork gateway used the real organization backend, with its main and small roles mapped to `skoda-llm-primary` and `skoda-llm-secondary`. A 40-prompt synthetic sample (20 per model; ten tasks and four wording variants) produced 39/40 schema-valid surfaces: main 19/20, small 20/20. The invalid main response supplied a single-select where multi-select was required; fallback remains necessary. Completed-response latency including the local gateway was main p50 3129 ms/p95 4766 ms and small p50 2375 ms/p95 2948 ms. The review script also checks the supplied synthetic table/chart values, dependency edges, options, defaults and card status: 39/40 passed these narrow task-specific checks. This is not a human usability or accessibility study, does not exercise streaming and is too small and repetitive to generalize quality. The initial 38/40 sample exposed an omitted read-only text primitive; the refined sample adds it. Reproduce with `spike.mjs` and `spike-review.mjs`; the JSON results contain only synthetic prompts and surfaces, not credentials.

The existing real-gateway test first returned 503 because its default role mappings named unavailable placeholder models and discovery had not completed. The spike waits for discovery and maps the roles explicitly in its in-memory harness; it does not change production configuration. An initial unpaced sample encountered the gateway's rate limit; the recorded sample is paced and every request returned HTTP 200.

For development acceptance, the user chose the current i7 workstation with the benchmark process pinned to four logical cores (2026-11-14). A representative surface of 100 table rows, 100 chart points and 20 controls should validate and first render within 200 ms p95 after the complete block is available, measured over 30 warm iterations; scrolling a 200-message Thread should retain the native UI's existing 60 fps target. Measure incremental memory and report it against client/desktop-host's normative budgets; these are acceptance targets, not current measurements. Exercise keyboard, UI Automation, high contrast and Czech/German/English application chrome. The production i5/16 GB baseline remains unverified until measured on that hardware; four-core affinity does not make this i7 equivalent. No fake success is inferred from a model-only or parser-only test.

**Preliminary native sketch (2026-11-14):** The available development host reports an Intel Core i7-12700, not the specified i5 baseline. `native-spike.cpp` uses existing debug-build native libraries in an offscreen 1100×800 surface containing 200 synthetic message labels, a 100-row Markdown table, a drawn 100-point line, a four-node drawn diagram and 20 checkboxes. Thirty synthetic scroll/repaint iterations measured p95 2.27 ms, maximum 2.30 ms and approximately 13.3 MB additional process working set; the element-tree accessibility checker reported zero issues and a checkbox responded to a simulated Space key. These are observations on this host, not first-render validation, a frame-pacing measurement, a real Thread, a chart/diagram accessibility audit, or evidence that the complete client meets the 150 MB budget. The chart and diagram are drawings without real data alternatives. Baseline-hardware, real UI Automation, complete surface rendering and integrated-client measurements remain outstanding.

**Four-core native sketch (2026-11-14):** With the process affinity verified as four logical CPUs (mask 15), thirty warm surface builds and offscreen first paints measured p95 4.55 ms, maximum 4.93 ms; thirty scroll/repaint iterations measured p95 5.49 ms, maximum 6.11 ms. Additional working set was 17,334,272 bytes. The element-tree checker found no issues, simulated Space toggled the first checkbox, and a real UI Automation client found the chart and diagram names as groups and the option as a checkbox. These synthetic measurements exclude schema validation, include only whatever the offscreen viewport paints, do not measure frame pacing, and do not establish accessible data alternatives or the complete client's memory budget. The prototype budgets are not known to fail, but the integrated implementation must measure validation, full rendering, meaningful UI Automation patterns and alternatives, frame pacing, total footprint, high contrast and localization in task 5.3. The i5 production baseline remains unverified.

**Real-gateway acceptance (2026-11-15):** The opt-in `gateway-acceptance.mjs` harness ran the native client against an isolated local control plane connected to the configured organization model, using synthetic information and a mock mail Tool. It observed the generated native comparison table, local sorting, a reviewed follow-up, a structured Question and the existing policy Approval card; the test rejected the Approval and passed in 29.7 seconds. A separate runtime test checks that a generated request cannot resolve the Approval through the Question route. This is one automated scenario, not a usability study or evidence of external mail delivery. The first attempt exposed a test token lifetime above the control plane's limit; the harness now checks authentication before launching the client.

The same isolated gateway scenario passed again after the fallback and Settings changes, in 15.8 seconds, with the same synthetic table, local sort, reviewed follow-up, structured Question and policy Approval observations.

**Integrated four-core measurement (2026-11-15):** The release-mode native test process verified four logical CPUs and opened a synthetic 200-message Thread with a 100-row table, 100-point line chart and 20 switches. Across 30 warm opens, first paint was 81.41 ms p95 (82.99 ms maximum); process working set was 26.3 MB before the window and 95.3 MB afterward (69.0 MB increase). Across 300 scroll calls, p95 was 16.77 ms, p99 17.84 ms and maximum 19.89 ms. The first test used a 16.7 ms p95 wall-time threshold and failed. That threshold is inconsistent with the existing `add-native-ui` validation method: `Present(1, 0)` waits for the 60 Hz refresh, so that design counts frames over 25 ms (1.5 periods) as dropped. Apply that existing method to the integrated test, requiring no frame over 25 ms in 300 measured frames, and still report p95, p99 and maximum. The original sample had zero frames over 25 ms; rerun the corrected check before treating it as passed. This method is a display-paced proxy rather than a direct compositor frame-statistics measurement. The test process includes fixture services and is not a measurement of the complete shipped client. The i5 production baseline remains unverified.

**Corrected rerun (2026-11-15):** With four logical CPUs verified in the release test process, 30 warm opens measured 77.77 ms p95 and 78.02 ms maximum. The 300 scroll samples had p50 16.67 ms, p99 17.68 ms, maximum 19.13 ms and zero over 25 ms, passing the established display-paced criterion. Working set rose from 26.4 MB to 96.1 MB (69.8 MB). The same fixture, compositor-measurement and baseline-hardware limitations above apply. Later implementation changes still require relevant acceptance checks before rollout.

**After incomplete-response fallback (2026-11-15):** The same four-core release fixture measured first paint at 82.66 ms p95 and 89.37 ms maximum; 300 scroll samples had p50 16.66 ms, p99 17.70 ms, maximum 19.49 ms and zero over 25 ms. Working set rose from 26.3 MB to 95.1 MB (68.8 MB). This remains a test-process measurement on the i7, not an i5 baseline or the complete shipped client's footprint.

**Final integrated checks (2026-11-15):** After the Settings integration, the four-core release test process measured 30 warm opens at 112.99 ms p95 (113.45 ms maximum). The 300 scroll samples had p50 16.67 ms, p99 18.92 ms, maximum 20.84 ms and zero over 25 ms. Working set rose from 47.8 MB to 101.6 MB (53.8 MB); earlier tests ran in the same process. Native Thread tests exercised UI Automation roles and chart/diagram data alternatives, Tab access to a switch and button, and English, Czech and German review text under a simulated high-contrast theme. Component checks also covered high-contrast system colors and the slider range. The theme is simulated rather than a test of changing the Windows setting, and the fixture and display-paced proxy limitations above still apply. The production i5 baseline and the complete shipped client's footprint remain unverified.

Roll out behind a client-side feature switch that defaults off until the spike, tests and local real-model acceptance pass; disabled or older clients show ordinary Markdown/code fallback. Deploy the schema and renderer together; preserve stored original messages for downgrade. If disabled after use, stored responses remain readable and no generated controls are active. Storage migration must preserve existing Threads; retain submitted message and Question history on rollback.

The release client exposes this switch in General Settings, stored locally and defaulting to off. The setting applies at the next client restart, which keeps the runtime prompt, host RPC capabilities and native rendering on the same immutable configuration for the entire session; Settings explains the restart. Development builds retain the existing command-line override for isolated acceptance tests.

**Specification reconciliation:** `client/work-inbox` owns presentation, Citation interaction and the user setting; `client/agent-runtime` owns structured Question responses, durable submissions and routing. The existing streaming Markdown and live-feed rules remain in force until a complete stored assistant answer can be rendered as a surface. Existing free-text Questions, message queueing and steering, and policy-enforced Approvals remain authoritative. The generated surface requirements add to these behaviors rather than replacing them.

**Alternatives:** Enable for all users immediately (unproven model compliance and latency); depend only on synthetic JSON (does not measure model behavior); a remote-only benchmark (does not verify native rendering or resource budgets).

## Risks / Trade-offs

- [A model produces invalid or unhelpful surfaces] -> Enforce schema and size limits, keep readable fallback and evaluate real configured models before enabling.
- [Generated visual content misrepresents data or evidence] -> Display values and units, expose actual Citations, reject invented references and retain prose/source inspection; the UI does not certify truth.
- [Prompt injection or a deceptive button causes a privileged action] -> Activate only host-bound assistant surfaces; treat labels and submissions as untrusted user intent and preserve policy-owned approvals.
- [State loss, stale events or double clicks repeat a submission] -> Persist revision-bound drafts and atomic idempotent acceptance; revalidate on the host after restart.
- [Native controls, charts or diagrams violate accessibility or footprint targets] -> Use UI Automation, keyboard and text alternatives; run baseline performance and accessibility acceptance before rollout.
- [The schema becomes a vendor lock-in] -> Version it, keep fallback and document decisions informed by A2UI; support future adapters as separately specified changes.

## Migration Plan

Add backward-compatible local storage and Run/Question data, preserving existing text events and Questions. Deliver parsing, rendering and submission behind the disabled feature switch; validate restored old Threads, Questions, disabled mode and downgrade. Enable only after acceptance; rollback by disabling the switch and retaining original stored message and submission data.

**Downgrade-compatible storage decision:** The database opener rejects schema versions newer than the client knows, so the provisional `app.db` migration must be removed. Reuse the existing `thread_attachments` storage as an internal, versioned record type: store a DPAPI-protected payload inside the already encrypted database, use a reserved identifier namespace and never publish its identifier as a user attachment or a Tool result. Native attachment APIs reject this reserved namespace; the additional protection also prevents an older client that happens to read a record from exposing its plaintext. Each record is bound to its Thread, Run, event sequence, block, content revision and, for an action, the button. Hash that binding into a domain-separated primary key, so the existing table's primary-key constraint prevents duplicate records. The protected action payload contains a random host-generated idempotency token and accepted outcome. Validate and update it in the same `app.db` transaction as the ordinary queued message or Question resolution. Thread deletion already deletes all Thread attachments, including under the older client; verify this with the older code path. Store the format version in the protected envelope, reject unknown versions, and migrate supported versions transactionally when necessary. Upgrading an existing database creates records only on first use and does not alter the database schema or its version.

This decision preserves the existing versioned Schema Migration rule: no new or modified SQL schema is introduced, so no SQL schema migration is necessary. It also avoids cross-file atomicity: `app.db` uses WAL, and [SQLite's WAL documentation](https://www.sqlite.org/wal.html) states that transactions across attached databases are not atomic as a set. Test old-database opening, protected payloads, old-client deletion and fallback, concurrent duplicate acceptance, restart retries and rollback before completing tasks 4.1, 4.4 or 5.1. Reject oversized records and avoid retaining old draft snapshots when updating a record.
